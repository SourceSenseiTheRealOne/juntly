# Durable Internal User Mapping Design

**Status:** Approved for implementation planning

## Purpose

Create a minimal, durable, provider-isolated mapping from a Clerk-verified session subject to one opaque internal Juntly user ID. This mapping is the required ownership primitive for later provider profiles, listings, orders, and other marketplace resources.

## Scope

This slice adds only:

- project-owned Supabase PostgreSQL migration history;
- an Ent representation of one internal-user mapping;
- a Go reconciliation service and race-safe repository;
- Clerk bearer-token verification at the Go API boundary;
- an authenticated, same-origin Next.js BFF reconciliation endpoint;
- OpenAPI/client types and layered verification.

This slice deliberately excludes profiles, display names, emails, roles, tiers, organisations, Clerk metadata writes, webhooks, listings, provider/customer ownership, payments, and marketplace data.

## Branch and integration topology

The implementation branch is `feature/internal-user-mapping`.

It requires these immutable local predecessors:

- `727f288` — health/API foundation, already integrated into local `development`.
- `e154f44` — localized Clerk identity foundation, currently on `feature/clerk-identity`.

Before feature code starts, the mapping branch must consume both predecessors as a stacked local branch. The Clerk source must not be duplicated or recreated. The existing health endpoint remains public and unchanged.

No remote branch update, pull request, deployment, remote Supabase migration, or Clerk resource/metadata mutation is in scope.

## Trust and data flow

```text
Authenticated browser
  → same-origin Next.js BFF
  → current Clerk bearer token (server obtained)
  → Go reconciliation endpoint
  → Clerk token verification
  → verified Clerk subject
  → reconciliation service
  → Ent repository
  → Supabase PostgreSQL internal_users row
```

### Authority rules

1. The browser never sends a Clerk subject, user ID, role, email, profile field, or internal ID.
2. The BFF calls `await auth()` and obtains a current token only after session validation.
3. The BFF forwards the token only to server-only `JUNTLY_API_ORIGIN`.
4. Go verifies every bearer token independently through the pinned Clerk Go SDK and accepts only a valid session with an allowed authorized party.
5. The verified `sub` becomes a typed `VerifiedIdentity` value. No other Clerk claims enter the mapping domain.
6. The database contains no bearer token, session, raw provider payload, email, display name, or metadata.

The canonical browser-facing local auth origin stays `http://localhost:4200`.

## Database model

A forward-only migration creates `public.internal_users`:

```sql
id uuid primary key,
clerk_subject text not null unique,
created_at timestamptz not null,
updated_at timestamptz not null
```

Rules:

- `id` is generated by trusted application code as a UUID; it is opaque and not caller-controlled.
- `clerk_subject` is a nonempty, bounded Clerk `sub`, unique and immutable after insertion.
- `created_at` is immutable.
- `updated_at` is application-owned; this slice does not synchronise a user profile.
- A subject lookup is indexed through the unique constraint.
- SQL under `supabase/migrations/` is the authoritative, ordered history. Ent schema/code must match it exactly.
- The API must not run automatic schema creation or migration at startup.

## Reconciliation contract

The provider-neutral application interface is:

```go
type VerifiedIdentity struct {
    Subject string
}

type InternalUser struct {
    ID        uuid.UUID
    CreatedAt time.Time
}

type Repository interface {
    FindBySubject(context.Context, string) (InternalUser, bool, error)
    Create(context.Context, string) (InternalUser, error)
}

type Service interface {
    Reconcile(context.Context, VerifiedIdentity) (InternalUser, bool, error)
}
```

Behavior:

1. Validate an empty or oversized subject before repository access.
2. Return an existing mapping unchanged with `created=false`.
3. Create one mapping for a previously unseen verified subject with `created=true`.
4. If concurrent requests collide on unique subject creation, reload the exact winning mapping and return it with `created=false`.
5. Map unknown persistence failures to a controlled dependency failure, never a successful reconciliation.

## HTTP contract

OpenAPI adds the body-less endpoint:

```text
POST /api/v1/auth/reconcile
Authorization: Bearer session-token
```

Responses:

| Status | Body | Meaning |
|---|---|---|
| `200` | `{ id: UUID, createdAt: RFC3339 timestamp }` | Existing or newly created mapping. The response intentionally does not reveal the Clerk subject. |
| `401` | Closed unauthenticated error envelope | Token absent, invalid, expired, malformed, or unauthorized party. |
| `503` | Existing privacy-safe service-unavailable envelope | Database or dependency failure. |

The BFF defines an equivalent same-origin route. It accepts no browser body and returns only the documented mapping response. It converts upstream failures, malformed data, request-ID mismatches, missing backend origin, and token-forwarding failure into an allowlisted error envelope. It never emits an upstream URL, bearer token, subject, Clerk diagnostic, database diagnostic, or stack trace.

## Configuration

Tracked files contain variable names and safe placeholders only.

Server-only runtime variable names:

```text
JUNTLY_API_ORIGIN
DATABASE_URL
CLERK_SECRET_KEY
CLERK_JWT_KEY            # optional networkless verification
CLERK_AUTHORIZED_PARTIES
```

Credentials, database URLs, generated Supabase keys, and token material remain only in ignored local configuration or process environments. They must not be read, printed, staged, committed, or copied into test fixtures.

## Verification requirements

Every behavior follows RED → GREEN → REFACTOR.

1. Migration contract test: one table, UUID ID, immutable unique subject, timestamps, and lookup constraint/index.
2. Ent schema test: generated model maps exactly to migration semantics.
3. Service tests: invalid subject rejects before repository calls, first creation, repeat idempotency, unique-conflict winner reload, and controlled persistence failure.
4. Authentication middleware tests: absent/malformed token, verifier failure, missing subject, unauthorized party, and verified-subject context propagation. Tests use synthetic fakes, never real tokens.
5. Handler/OpenAPI tests: body-less closed endpoint, `401` before service invocation, documented `200`, and privacy-safe `503`.
6. BFF tests: signed-out rejection, missing token, valid safe forwarding, malformed upstream rejection, and no upstream topology leakage.
7. Disposable local Supabase/PostgreSQL integration: apply the complete migration chain; concurrently reconcile one synthetic subject; prove one row, one stable opaque UUID, stable creation time, and no duplicate mapping.
8. Real local browser proof is separate: with an approved development test user, call the same-origin BFF twice and record only HTTP status, request IDs, stable opaque-ID equality, creation-time equality, and row count. Do not record subject, email, cookie, bearer token, or database URL.

## Non-goals and follow-on boundary

A successful mapping only proves durable identity reconciliation. It does not prove an authenticated browser session until a real approved test-user journey runs, and it does not authorize marketplace work by itself. Provider profiles, listings, ownership edges, payments, and entitlements start only in later approved slices after this mapping is durable and verified.
